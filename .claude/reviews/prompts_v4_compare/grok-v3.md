===== v1 만료 전에는 로그아웃이 아니다: 스테이트리스 액세스 토큰의 무효화 경계 =====
<!-- sec:intro -->

## 로그아웃 버튼을 눌러도 검증기는 같은 답을 낸다

JWT로 로그인을 붙여 본 개발자라면 헤더와 페이로드를 디코드해 본 적이 있다. 페이로드의 `exp`는 만료 시각이고, 단위는 초다. 그 숫자가 현재 시각보다 미래이면, 폐기 목록이 없는 검증기는 이 요청을 거절할 이유가 없다.

액세스 토큰을 쓰면 세션 저장소가 필요 없다는 관행이 그 다음을 망친다. 그 문장은 조회를 없애자는 말인데, 로그아웃과 탈취 대응까지 만료 시각에 떠넘긴다.

개발자가 로그아웃 처리에서 지우는 행을 검증 함수가 읽지 않으면, 그 삭제는 다음 요청의 서명 검사에 닿지 않는다. 검증기가 읽는 것은 클라이언트가 다시 보내는 문자열과, 그 안의 만료 시각뿐이다.

서명만 검사하는 스테이트리스 액세스 토큰에서 서버는 만료 시각 이전에 그 토큰 하나만 폐기하지 못한다. 무효화 경계는 로그아웃을 누른 시각이 아니라 `exp`다. 그 시각이 오기 전에 같은 문자열이 다시 들어오면, 검증기는 로그인된 요청과 같은 이유로 통과시킨다.

<!-- sec:body-1 -->

## 스테이트리스는 서버가 지웠다는 뜻이 아니다

개발자가 스테이트리스라고 부를 때, 그 말은 서버가 발급 결과를 요청마다 조회하지 않는다는 뜻이다. 서버는 비밀 키로 클레임을 서명하고, 그 문자열을 클라이언트에 넘긴 뒤, 발급했다는 사실을 검증 경로에 남기지 않는다.

서버가 사본을 갖고 있지 않으면 개발자는 삭제로 그 토큰만 무효화하지 못한다. 세션 테이블에서 행을 지워도, 검증 함수의 인자에는 토큰 문자열과 비밀 키와 현재 시각만 있다. 읽지 않는 테이블의 삭제는 검증 결과를 바꾸지 못한다.

클라이언트가 자기 화면에서 토큰을 지우는 일도 서버의 폐기가 아니다. 그 문자열의 복사본을 다른 쪽이 들고 있으면, 그 복사본으로 온 요청도 같은 서명을 갖고 있다. 검증기는 누가 보관했는지를 구분하지 않는다.

그래서 서버에서 세션을 지웠으니 로그아웃됐다는 문장은, 검증 경로를 확인하기 전에는 성립하지 않는다. 지운 저장소와 읽는 함수가 다르면, 로그아웃 버튼은 장식으로 남는다.

세션이 필요 없다는 문장은 조회를 없앤다는 뜻까지만 참이다. 조회를 없애면 개별 거절이 앉을 자리도 같이 사라진다. 첫 문장이 두 번째 결과를 대신 설명해 주지는 않는다.

## 서명이 맞으면 거절 조건은 만료 시각뿐이다

경계를 코드로 고정하면, 관행이 어디를 검증기 밖에 두는지 보인다.

아래 모듈의 서명은 HS256이다. HS256은 공유 비밀 키와 SHA-256으로 HMAC를 만드는 방식이다.

이 모듈의 검증 함수는 세션 저장소나 거부 목록을 인자로 받지 않는다. 발급 함수도 만든 문자열을 어디에도 넣지 않는다.

<!-- sec:code-1 -->
```python
import base64
import hashlib
import hmac
import json
import time
from typing import Any, Optional


def _b64url_decode(segment: str) -> bytes:
    padding = '=' * (-len(segment) % 4)
    return base64.urlsafe_b64decode(segment + padding)


def _b64url_encode(raw: bytes) -> str:
    return base64.urlsafe_b64encode(raw).rstrip(b'=').decode('ascii')


class TokenRejected(Exception):
    def __init__(self, reason: str) -> None:
        super().__init__(reason)
        self.reason = reason


def issue_access_token(
    secret: bytes,
    subject: str,
    ttl_seconds: int,
    now: Optional[int] = None,
) -> str:
    if now is None:
        now = int(time.time())
    if ttl_seconds <= 0:
        raise ValueError('ttl_seconds must be positive')
    header = {'alg': 'HS256', 'typ': 'JWT'}
    payload = {'sub': subject, 'iat': now, 'exp': now + ttl_seconds}
    header_b64 = _b64url_encode(
        json.dumps(header, separators=(',', ':')).encode('utf-8')
    )
    payload_b64 = _b64url_encode(
        json.dumps(payload, separators=(',', ':')).encode('utf-8')
    )
    signing_input = f'{header_b64}.{payload_b64}'.encode('ascii')
    signature = hmac.new(secret, signing_input, hashlib.sha256).digest()
    return f'{header_b64}.{payload_b64}.{_b64url_encode(signature)}'


def verify_access_token(
    token: str,
    secret: bytes,
    now: Optional[int] = None,
) -> dict[str, Any]:
    if now is None:
        now = int(time.time())
    parts = token.split('.')
    if len(parts) != 3:
        raise TokenRejected('malformed')
    header_b64, payload_b64, signature_b64 = parts
    try:
        header = json.loads(_b64url_decode(header_b64))
        payload = json.loads(_b64url_decode(payload_b64))
        presented = _b64url_decode(signature_b64)
    except (json.JSONDecodeError, ValueError) as exc:
        raise TokenRejected('malformed') from exc
    if not isinstance(header, dict) or header.get('alg') != 'HS256':
        raise TokenRejected('alg')
    if not isinstance(payload, dict):
        raise TokenRejected('malformed')
    signing_input = f'{header_b64}.{payload_b64}'.encode('ascii')
    expected = hmac.new(secret, signing_input, hashlib.sha256).digest()
    if len(presented) != len(expected) or not hmac.compare_digest(
        expected, presented
    ):
        raise TokenRejected('signature')
    exp = payload.get('exp')
    if isinstance(exp, bool) or not isinstance(exp, int):
        raise TokenRejected('exp')
    if now >= exp:
        raise TokenRejected('expired')
    return payload


def logout_local(session_store: dict[str, str], subject: str) -> None:
    session_store.pop(subject, None)


def accepted_after_local_logout(
    secret: bytes,
    subject: str,
    ttl_seconds: int,
    now: int,
) -> bool:
    session_store: dict[str, str] = {}
    token = issue_access_token(
        secret,
        subject,
        ttl_seconds,
        now=now,
    )
    session_store[subject] = token
    logout_local(session_store, subject)
    try:
        verify_access_token(token, secret, now=now)
    except TokenRejected:
        return False
    return subject not in session_store
```

발급 함수를 검증과 같은 모듈에 둔 이유는, 서버가 문자열을 만들고 검증 경로에는 남기지 않는 쪽을 코드로 보이게 하기 위해서다. `issue_access_token`의 반환값 외에 발급 기록은 없다.

헤더와 페이로드는 JSON 객체다. 발급 함수는 그 객체를 공백 없는 JSON 문자열로 직렬화한다. 키 순서가 바뀌면 서명 입력이 바뀌므로, 딕셔너리에 넣은 순서를 그대로 쓴다.

그 문자열을 세그먼트로 만들 때 쓰는 인코딩이 base64url이다. 개발자가 페이로드를 디코드할 때 이미 거친 인코딩의 역방향이다. 패딩 문자는 떼고 붙인다. 검증 쪽은 그 역을 풀어 헤더와 페이로드를 다시 객체로 만든다.

서명 입력은 헤더 세그먼트와 페이로드 세그먼트를 점 하나로 이은 바이트열이다. 서버는 그 입력으로 HMAC를 만들어 세 번째 세그먼트로 붙인다. 세 조각을 점으로 이은 문자열이 클라이언트가 들고 가는 액세스 토큰이다.

페이로드에 넣는 만료는 현재 시각에 수명을 더한 값이다. 수명인 `ttl_seconds`는 발급을 호출하는 쪽이 고른 초다. 이 값을 크게 넘기면, 아래 검증이 통과시키는 구간이 그 값만큼 길어진다. 0 이하는 발급 전에 거절한다. 만료가 발급 시각과 같거나 과거인 토큰을 만들어 놓고 짧은 만료라고 부르지 않기 위해서다.

검증은 세 세그먼트가 아니면 바로 거절한다. 이어서 헤더와 페이로드를 디코드한다. 이 디코드는 개발자가 이미 해본 디코드와 같고, 아직 서명을 믿기 전이다. 디코드가 깨지면 이유는 `malformed`다.

헤더의 `alg`가 HS256이 아니면 거절한다. 발급 함수가 실제로 서명한 방식만 받기 위해서다. 알고리즘을 다른 것으로 바꾸는 절차는 범위 밖이라, 모듈은 교체 경로를 두지 않고 불일치를 거절로 끝낸다.

서명이 필요한 이유는, 디코드된 페이로드만으로는 발급자가 그 만료 시각을 썼는지 알 수 없기 때문이다. 검증 함수는 헤더 세그먼트와 페이로드 세그먼트를 다시 HMAC해서 기대 서명을 만든다.

제시된 서명과 길이가 다르면 거절한다. 길이가 같으면 `hmac.compare_digest`로 맞춘다. 응답 시간으로 불일치 위치를 흘리지 않으려고 상수 시간에 비교한다. 서명이 다르면 이유는 `signature`다.

서명이 맞는 순간, 이 함수에는 개별 토큰을 골라 거절하는 분기가 없다. 남는 거절 조건은 `exp`다. 값이 정수가 아니면 거절한다. 파이썬에서 불리언은 `int`의 하위 타입이라, 참이 만료 시각으로 새지 않게 불리언도 거절한다.

현재 시각이 `exp`보다 앞서지 않으면 거절한다. 비교는 현재 시각이 만료 시각 이상인지다. JWT 명세는 현재 시각이 만료 시각보다 앞설 것을 요구하므로, 같은 초도 이미 만료다. 이 모듈은 여유 초를 더하지 않는다.

`iat`는 발급 시각으로 페이로드에 남기지만 거절 조건이 아니다. 발급 시각을 안다고 그 토큰만 지금 막지는 못한다. 검증 함수가 반환하는 것은 폐기 여부가 아니라, 서명과 만료를 통과한 페이로드다.

검사 순서를 바꾸면 이 경계가 흐려진다. 만료를 서명보다 먼저 보면, 서명이 틀린 토큰인데도 만료가 지났으면 이유가 만료로 기록된다. 이 모듈은 서명을 먼저 확인하고 그 다음에만 `exp`를 본다. 통과한 토큰은 비밀 키를 가진 쪽이 넣은 만료 시각을 가진다. 그 시각 이전의 거절은 이 순서 안에 들어올 자리가 없다.

로컬 삭제가 검증을 바꾸지 않는지를 호출로 확인하려고 함수를 하나 더 둔다. `accepted_after_local_logout`은 발급된 토큰을 딕셔너리에 넣었다가 `logout_local`로 지운다. `verify_access_token`은 그 딕셔너리를 받지 않는다. 수명이 양수이고 현재 시각이 발급 시각과 같으면 검증은 예외 없이 페이로드를 돌려주고, 함수는 참을 반환한다. 맵에서 키가 사라진 것과 검증 성공이 동시에 성립한다.

같은 관계를 표로 고정하면, 로그아웃이 이유 코드에 안 나오는 지점이 분명해진다.

| 검증기가 본 것 | 로그아웃이 지운 것 | 결과 |
| --- | --- | --- |
| 서명 일치, 현재 시각이 exp 미만 | 세션 행 또는 로컬 맵 | 통과 |
| 서명 일치, 현재 시각이 exp 이상 | 아무것도 안 지움 | 거절, 이유 expired |
| 서명 불일치 | 아무것도 안 지움 | 거절, 이유 signature |
| 세그먼트 손상 | 세션 행 | 거절, 이유 malformed |

이유 코드에 로그아웃은 없다. 개발자가 지운 저장소는 검증 결과의 이름으로 등장하지 않는다.

## 짧은 만료가 줄이는 것은 탈취 뒤의 남은 창이다

토큰 문자열이 새어 나간 뒤 개발자가 그 문자열만 막으려면, 검증기가 그 문자열을 알아봐야 한다. 서명만 보는 검증기에는 그 분기가 없다. 공격자가 같은 문자열을 다시 보내도, 서명이 맞고 만료 전이면 검증기는 사용자 클라이언트의 요청과 같은 이유로 통과시킨다.

남은 창의 시작은 발급 시각이 아니다. 공격자가 그 문자열을 쓰기 시작하는 시각부터 만료 시각까지다. 발급 직후부터 탈취 전까지는 이미 지난 구간이라, 공격자가 그 구간을 소급해서 열지는 못한다.

아래 JSON은 수명을 60초로 둔 페이로드 예시다. 운영 중 측정값이 아니다. `iat`와 `exp`의 차이가 발급 시점의 최대 창이라는 것을 숫자로 고정하려고 넣은 것이다.

<!-- sec:code-2 -->
```json
{
  "sub": "user-17",
  "iat": 1710000000,
  "exp": 1710000060
}
```

이 블록은 서명이 붙은 토큰이 아니라, 발급 함수가 서명하기 전의 페이로드다. 세 번째 세그먼트가 없으므로 검증 함수에 넣으면 `malformed`로 거절된다.

`sub`는 주체 식별자다. 누가 로그인했는지를 담을 뿐, 그 주체의 토큰을 지금 폐기하라는 표시는 아니다. `exp`가 1710000060이면, 검증기에 넣는 현재 시각이 그 값보다 작은 동안 이 페이로드가 반환된다.

남은 창은 만료 시각에서 탈취 시각을 뺀 값이다. 이 샘플에서 탈취 시각을 1710000030으로 두면 남은 창은 30초다. 발급 시 수명 60초 전체가 공격자에게 열리는 계산이 아니다. 그래도 그 30초 동안 서버는 이 문자열만 골라 거절하지 못한다. 사용자에게 남은 정상 요청도 같은 30초를 통과한다.

개발자가 만료를 짧게 잡으면 그 남은 구간이 줄어든다. 폐기 API가 생기지는 않는다. `ttl_seconds`를 60에서 3600으로 바꾸면, 같은 방식으로 계산한 남은 창의 끝이 한 시간 쪽으로 밀린다. 검증기가 `expired`를 내기 시작하는 시각이 밀리는 것이다.

만료를 짧게 했으니 로그아웃이 된다는 말은 두 사건을 섞는다. 짧은 만료는 창을 줄인다. 로그아웃은 검증 경로에 개별 거절이 있을 때만 그 시각에 창을 닫는다. 이 모듈의 검증 경로에는 그 거절이 없다.

## 만료를 길게 잡는 관행이 그 창을 다시 연다

세션 테이블을 없앴다는 이유로 액세스 토큰 수명을 몇 시간이나 며칠로 두는 선택을 개발자들이 자주 한다. 갱신 요청을 줄이려는 편의다. 그 편의는 앞에서 줄이려던 창을 검증기 쪽에 다시 열어 둔다.

수명이 길면 로그아웃 시각과 `exp` 사이에 들어오는 요청이 늘어난다. 사용자는 이미 로그아웃 버튼을 눌렀다. 검증기는 그 사실을 페이로드에서 읽지 못한다. 이미 서명된 문자열의 `exp`를 비밀 키만으로 앞당기지도 못한다. 서명은 발급 당시의 바이트에 묶여 있다.

페이로드에 폐기 플래그를 넣고 싶어하는 경우도 같은 벽에 부딪힌다. 발급 시점의 값은 거짓이다. 로그아웃 뒤에 서버가 이미 나간 문자열의 필드를 고칠 방법은 없다. 클라이언트가 옛 문자열을 그대로 내면, 검증기가 읽는 필드는 발급 당시의 값이다.

비밀 키를 통째로 바꾸면 기존 서명이 모두 어긋난다. 그건 한 사용자의 로그아웃이 아니다. 그 키로 서명한 액세스 토큰은 모두 같은 시각에 서명 불일치로 거절된다. 개별 무효화가 필요해서 키를 버리는 선택은, 서명만 보는 검증이 하나를 골라 막지 못한다는 사실을 다른 비용으로 인정하는 일이다. 키를 교체하는 운영 절차는 이 글에서 구현하지 않는다.

긴 만료를 세션 제거의 대가로 부르면 비용의 위치가 가려진다. 비용은 저장소가 줄어든 자리에 있지 않다. 탈취 뒤와 로그아웃 뒤에 검증기가 통과시키는 구간에 있다. 그 구간을 늘리는 쪽은 라이브러리가 아니라, 수명을 크게 넣어 발급을 호출하는 쪽이다.

<!-- sec:tradeoff -->

## 이 경계 밖에서 치러야 하는 비용

개발자가 만료를 짧게 잡으면 탈취 창은 줄고 재발급 횟수는 늘어난다. 클라이언트가 새 액세스 토큰을 받는 통로, 그중 리프레시 토큰을 회전시키는 구현은 이 글의 범위 밖이다. 회전 없이 짧은 `exp`만 두면 사용자는 만료마다 다시 로그인해야 한다. 그 불편을 이유로 수명을 늘리면, 본문이 말한 창이 다시 열린다.

서명 알고리즘을 교체하는 일도 범위 밖이다. 모듈은 발급과 검증이 같은 HS256, 같은 비밀 키라는 전제만 둔다. 알고리즘 이름을 실어 마이그레이션하는 코드는 없다.

쿠키와 웹 스토리지 중 어디에 둘지도 범위 밖이다. 저장 위치는 문자열이 새는 경로를 바꾸지만, 검증 함수가 폐기 목록을 조회하지 않으면 만료 전 개별 거절은 생기지 않는다. 위치를 고르는 일이 무효화 경계를 `exp`에서 로그아웃 시각으로 옮기지는 못한다.

서버 시각이 토큰을 가진 쪽의 시각보다 앞서면, 그 쪽이 아직 유효하다고 보낸 요청을 서버가 만료로 거절한다. 이 모듈은 그 오차를 흡수하는 여유 초를 더하지 않는다.

여유 초를 넣으면 그 조기 거절은 줄어든다. 탈취 뒤의 창은 그 초만큼 길어진다. 여유를 넣을지는 만료 경계를 어디까지 믿을지의 선택이지, 개별 폐기를 대신하는 장치가 아니다.

개별 폐기가 요구 사항이면 이 설계 안에 넣지 못한다. 토큰마다 식별자를 두고 요청마다 거부 목록을 찾는 순간, 검증은 더 이상 스테이트리스가 아니다. 목록 조회가 실패할 때 통과시킬지 거절할지, 만료된 목록 행을 언제 지울지, 목록의 수명을 `exp`와 어떻게 맞출지는 세션 저장소가 원래 지던 문제다.

그 문제를 검증 함수에서 지워 버리지 않는다. `verify_access_token`은 거부 목록 인자를 받지 않는다. 서명과 만료만으로 개별 로그아웃을 흉내 내는 분기도 없다. 개별 폐기가 필요하면 다른 검증 경로를 설계해야 하고, 그 경로는 이 글이 설명하는 메커니즘이 아니다.

<!-- sec:conclusion -->

## 무효화 경계는 삭제 시각이 아니라 만료 시각이다

서명만 검사하는 액세스 토큰에서 서버는 만료 전에 그 토큰 하나만 폐기하지 못한다. 로그아웃이 검증 경로 밖의 저장소를 비워도, 현재 시각이 `exp`보다 작으면 다음 요청은 통과한다.

탈취 뒤에 개발자가 이 설계 안에서 돌리는 나사는 수명이다. 그 나사를 풀어 만료를 멀리 두는 관행은 세션 제거 다음에 자동으로 따라오는 단계가 아니다. 무효화 경계를 미래로 미루는 선택이다.

짧은 만료를 넣었다는 문장은 로그아웃이 생겼다는 문장이 아니다. 검증기가 만료로 거절하기 시작하는 시각이, 이 토큰에 대해 로그아웃이 끝나는 시각이다.
