## 글별 판단

**Claude v4.** 슬롭은 아니다. v3 보다 내용이 낫다: 변경 전 경계 조건 다섯 개를 적어 두고 변경 후 테스트에 전부 남겼고, 카드 거절을 예외에서 반환값으로 바꾼 설계 이유, Jest 호이스팅·TDZ 마찰, "상태는 페이크로, 바깥 명령은 스파이로" 기준이 들어갔다. v3 의 거짓 주장("catch 의미가 바뀌면 이 테스트가 실패한다")에 해당하는 과장은 없고, 멱등 키 테스트가 보장하는 범위를 스스로 좁혀 말한다. 그러나 24,306자로 상한을 넘기고, 문체가 "~합니다"로 바뀌었으며(v3·블로그는 "~다"), 불릿이 10→27 개, "들어가며/마치며" 제목과 결론 요약이 돌아왔다. 주제 자체는 여전히 교과서적 포트·어댑터 이야기라 "읽을 가치"의 문제는 그대로다.

**Gemini v4.** 절반은 슬롭이다. "가장 먼저 점검하는 설정 중 하나가…"로 열고 "추상적인 이름 뒤에 숨겨진… 비로소 구축할 수 있다"로 닫는다. 문장이 길고 굵게가 많고 같은 말을 절마다 되풀이한다. 코드 3번은 두 함수와 스레드 잠금 하나로 만든 가짜 엔진(이름은 `MockMVCCEngine`이지만 버전도 Undo 도 없다)을 합친 260줄이고, 본문은 "위 검증 코드에서 확인할 수 있듯 변경 전 방식에서는 12,000원이 출금"이라 하지만 그 코드는 취약한 함수를 실행하지 않는다(본문-코드 어긋남). 음수 잔액 시나리오를 Write Skew 로 부른 것은 틀린 분류다. 핵심인 Read View 가시성 규칙과 "자기 UPDATE 가 최신 버전을 가시화하는" 동작은 v3 와 같고 정확하다. 길이는 v3 와 같은 패턴으로 상한을 넘겼다.

**Grok v4.** 슬롭이 아니고 셋 중 가장 낫다. 세션 저장소를 대조군으로 두고 같은 파일에서 두 `verify`를 비교하는 장치가 생겼고, 검증 순서 6단계와 그 순서를 단언하는 `demonstrate()`가 본문 주장과 1:1 로 맞는다. 집행하지 않는 클레임(`jti`, `nbf`)을 거절하는 이유, `now == exp`가 만료인 근거(RFC 7519), 시계 여유를 넣지 않은 이유를 다 적었다. 같은 명제를 여러 절에서 되풀이하는 버릇은 남았지만 v3 보다 덜하다. 가정과 범위 밖을 끝에 명시했다.

## 교차 발견

1. **길이가 늘었다.** v3 문장 규칙("분량은 주제를 넓히는 데 쓰지 않는다")을 빼고 "`assessment`·`evidence` 기준을 충족하라"와 "완전한 파일만 `python`/`typescript`로"를 넣은 결과로 보인다. 세 글 모두 코드가 늘었고 Claude 는 테스트 파일까지 완전본으로 썼다. 수정 프롬프트의 길이 예산만으로는 부족하고 작성 프롬프트에도 필요하다.
2. **문체 규칙이 없어 Claude 가 "~합니다"로 갔다.** v4 는 한국어 어미를 정하지 않는다. 블로그의 다른 글과 어긋난다.
3. **상투적 도입·결론이 돌아왔다.** `conclusion` 을 필수에서 뺐지만 셋 다 결론 절을 썼고, Claude·Gemini 는 "들어가며/마치며/결론:" 제목을 썼다. v3 에 있던 "상투적 도입·마무리 문구를 쓰지 않는다"가 v4 에는 없다.
4. **compare 도구가 잡은 결함 둘.** 옛 영수증 입력에 `level_criteria` 가 없어 비교가 시작도 못 했고(기본 기준표로 채움), Claude effort high 는 24,000 토큰 한도를 생각 토큰으로 다 써 본문이 비는데 `replay` 는 D-53 의 한도 올리기를 하지 않아 "Invalid JSON" 으로만 보였다(`--max-output-tokens`, 잘림 표시 추가). 운영 `call()` 은 한도를 올려 재시도하므로 WRITE_DRAFT:architect 는 매번 재시도 비용이 들 가능성이 있다. 라우트의 `max_output_tokens` 를 올리거나 effort 를 낮추는 쪽을 검토한다.

## 결론

v4 로 바꾼다고 "AI 슬롭"이 해소되지는 않는다. 세 글은 지어낸 사례·공허한 문구가 적고 핵심 메커니즘을 코드로 보여 주므로 슬롭급은 아니지만, v3 대비 뚜렷한 개선은 Grok 한 편이고 Claude·Gemini 는 길어져 게이트를 못 넘는다. 사용자가 본 "그렇게까지 작업했는데 겨우 이거야?"는 지시문 형식의 문제가 아니라 주제·근거의 문제라는 2026-11-06 진단과 같은 결론이다. `Settings.prompt_version` 은 이 시점에는 v3 로 둔다(2차 비교 뒤 사용자 결정으로 v4 로 올렸다). v4 디렉터리는 아직 배포 전이라 고칠 수 있다: 작성 프롬프트에 길이 예산(예: `max_chars` 의 60~75%)과 코드 비중 상한, 한국어 어미("~다"), 상투적 도입·결론 금지를 넣고 같은 영수증으로 다시 비교한다.

## 2차 비교: 작성 프롬프트 보강 뒤, 같은 영수증 (2026-11-07)

1차의 교차 발견 1~3 을 작성 프롬프트에 넣었다: 길이 예산(`max_chars` 는 상한, 목표는 60~70%, 코드 펜스 40% 이하, 완전한 파일은 대상 모듈이나 증명 스크립트 하나만, 같은 명제는 한 번만), 한국어 어미("~다", "~합니다"·명령형·완충 어미 금지), 불릿 대신 문단, 상투 도입·결론 요약·"들어가며/마치며/결론/요약" 제목 금지. 수정 프롬프트에는 어미 유지 한 줄을 넣었다(D-47 원칙). 같은 세 영수증을 가족마다 1회 다시 썼다(분산은 모른다). 글은 `prompts_v4_compare/{family}-v4-2.md` 다.

|---|---|---|---|---|---|---|---|
| Claude | 15,414 | 24,306 | 15,859 | 46% → 55% → 43% | 통과 / 실패 / **통과** | 10 → 27 → 8 | 79% |
| Gemini | 27,395 | 30,204 | 17,680 | 50% → 47% → 36% | 실패 / 실패 / **통과** | 8 → – → 0 | 88% |
| Grok | 10,076 | 13,405 | 14,607 | 32% → 44% → 34% | 통과 / 통과 / 통과 | – → – → 7 | 73% |

셋 다 "~다" 어미이고, 상투 도입·결론 요약·"들어가며/마치며" 제목이 없다. 마지막 섹션은 셋 다 기준·경계를 적는다. 완충 어미 검색은 Claude 의 "어긋날 수 있다" 한 건(요구가 아니라 가능성 서술이라 정당)뿐이다. 60~70% 목표는 아무도 맞추지 못했고 73~88% 에 섰다. 수정 여지는 Claude 4,141자, Gemini 2,320자, Grok 5,393자다.

**Claude 2차.** 여섯 편 중 가장 낫다. 1차의 내용(변경 전 제약 네 가지의 행방, 멱등 키의 포트 계약화, "상태는 페이크로·바깥 명령은 스파이로", 페이크가 PK 제약을 재현하지 못하는 한계)을 유지한 채 8,400자를 줄였다. 경로·형태·시점 결합 셋으로 `jest.mock` 의 비용을 설명하고, 호이스팅과 `mock` 접두사 규칙, `import type` 으로 뒤집힌 소스 의존 방향, 판별 유니온의 좁히기까지 사실이 맞는다. 평균 문장 37자. 남은 흠: 코드 5번 한 스니펫에 어댑터와 조립 지점 두 파일을 넣어 import 없는 식별자가 보인다. 길이는 목표보다 길다.

**Gemini 2차.** 1차의 슬롭 신호가 모두 사라졌다. 상투 도입("가장 먼저 점검하는 설정 중 하나가")·결론("비로소 구축할 수 있다") 없음, 쓰기 스큐를 두 계좌 합계 불변식으로 바로잡음, 260줄 가짜 엔진 대신 Barrier 로 두 스레드를 맞추는 92줄 하네스. Read View 가시성 규칙과 자기 UPDATE 의 가시화는 1차와 같이 정확하다. 남은 결함 둘: 코드 3번(`python-snippet`)이 들여쓰기 어긋남으로 `IndentationError` 다(격리 `ast.parse` 로 확인. 스니펫 태그라 게이트는 파싱하지 않는다). 하네스 소개 문장은 "원자적 연산 구현에서 정합성이 보존되는 것을 검증"한다고 하지만 하네스에 원자적 연산 변형이 없다(본문-코드 어긋남, 1차보다 작다). 문장은 여전히 길다(평균 96자, 세 가족 중 최장). 인라인 코드 문단당 5.7개.

**Grok 2차.** 어미·상투 문구는 문제없고 7단계 거절 순서와 `prove()` 의 단언이 대응하지만, 1차보다 나아졌다고 보기 어렵다. 코드 비중 상한을 지키느라 1차의 가장 좋은 장치였던 세션 저장소 대조군 코드가 사라지고 문단 설명으로만 남았다. 대신 "로그아웃은 verify 의 입력을 바꾸지 않는다"는 한 명제를 intro·body-1(아홉 문단)·body-3·body-4·tradeoff·conclusion 에서 되풀이한다. "같은 명제는 한 번만" 규칙이 Grok 에는 듣지 않았다. 본문-코드 어긋남 하나: 본문은 4번(페이로드가 객체가 아니면 `malformed`) 뒤에 5번(`alg` 검사)이라고 적지만 코드는 `alg` 검사가 먼저다. 주제가 자명한 사실(서명만 보는 토큰은 만료 전 개별 폐기가 안 된다)이라 14,600자를 채울 내용이 없다는 1차 판단은 그대로다.

### 교차 발견 (2차)

1. **프롬프트로 고칠 수 있는 결함은 고쳐졌다.** 길이·어미·불릿·상투 제목은 세 가족 모두 규칙대로 움직였다. v4 가 v3 보다 길어진 원인이 규칙 삭제였다는 1차 진단이 맞았다.
2. **백분율 목표는 느슨하게 지켜진다.** 60~70% 를 주면 73~88% 가 나온다. 수정 루프에서 더해질 양을 생각하면 Gemini 는 2,320자밖에 여유가 없다. 다음 수단은 말이 아니라 숫자다: 코드가 `structure_rules` 에 `target_chars`(예: `max_chars` 의 65%)를 넣어 주는 변경을 검토한다. 이번에는 하지 않았다.
3. **남은 결함은 프롬프트 형식의 문제가 아니다.** Gemini 의 스니펫 들여쓰기 오류와 하네스 과장, Grok 의 되풀이와 분기 순서 어긋남은 리뷰·사실 확인 단계가 잡아야 하는 종류다. 스니펫은 게이트가 파싱하지 않으므로 리뷰어 프롬프트가 코드 블록을 읽는지가 중요하다.
4. **코드 비중 상한의 비용.** Grok 은 대조군 코드를 버렸다. "증명 스크립트 하나만" 규칙이 대조 실험 두 편을 허용하지 않는다. 상한을 유지하되 "대조군이 주장을 증명하면 둘째 파일도 된다"로 풀 수 있다. 이번에는 바꾸지 않았다.

### 결론 (2차)

보강한 v4 작성 프롬프트는 세 가족 모두에서 v3 와 같거나 낫다: Claude·Gemini 는 뚜렷히 낫고 Grok 은 비슷하다. 1차의 "v4 로 바꾸면 Claude·Gemini 가 게이트를 못 넘는다"는 사라졌다. 그러나 "AI 슬롭" 진단의 나머지 절반인 주제·근거의 문제는 프롬프트가 건드리지 못했고, 이 비교는 WRITE_DRAFT 한 호출만 본다. 리뷰·수정·다듬기까지 거친 결과는 `PROMPT_VERSION=v4` 로 실제 라운드를 한 번 돌려야 안다. `Settings.prompt_version` 은 사용자 결정으로 v4 로 올렸다(2026-11-07). 되돌리기는 `PROMPT_VERSION=v3` 다.

## 3차 확인: 용어 표기 규칙 (Grok 영수증 1회, 2026-11-07)

사용자 지적: "스테이트리스"는 한국 개발 글에서 본 적이 없고 통용 표기는 "무상태(stateless)"다. 출처를 영수증으로 확인하니 작성자가 아니라 **주제 제안 단계**였다. 슬롯 C 의 `topic.title`·`core_mechanism` 에 "스테이트리스 액세스 토큰"이 박혀 있고(제안자는 Grok 자신), 작성자는 v3·v4 1차·2차 모두 그대로 따랐다(5·9·7회). v4 프롬프트 어디에도 용어 표기 규칙이 없었다.

주제 제안·작성 프롬프트 여섯 편에 규칙을 넣었다: 통용 한국어 용어가 있으면 그것(무상태, 갱신 손실, 멱등성), 없으면 영어 원어를 로마자로(Read View, HMAC), 임의 음차 금지, 첫 등장에 원어 병기. 작성 쪽에는 "`topic` 이 음차를 써도 통용 용어로 바꾸고 제목도 같이"를 덧붙였다. 같은 Grok 영수증(주제는 여전히 "스테이트리스")으로 1회 다시 쓴 결과: "스테이트리스" 0회, "무상태" 6회, 본문 첫 등장 "**무상태**(stateless)", 제목 "무상태 액세스 토큰의 무효화 경계". 13,696자(코드 32%), 게이트 통과, 코드 두 블록 파싱 통과. 남은 외래어(페이로드·액세스 토큰·클레임)는 통용 표기다. 글은 `prompts_v4_compare/grok-v4-3.md` 다.

규칙은 정적이다. 승인된 용어 사전이 생기면 그 표준 표기 목록을 두 프롬프트의 입력으로 넣는 경로가 다음이다(`agents_design/08_glossary_and_provenance.md`).
