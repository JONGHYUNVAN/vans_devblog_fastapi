# 01. 개요

## 1. 목표

- 라운드 하나당 서로 다른 주제의 기술 글 3편을 사람 개입 없이 발행 가능한 품질로 만든다.
- 각 글은 작성자가 아닌 두 에이전트의 **구조화된 리뷰**를 받고, 작성자는 리뷰를 수용하거나 근거를 들어 기각한다.
- 초안 → 리뷰 → 수용/기각 → 최종본의 이력을 전부 보존해 글 하단에 "AI 피어 리뷰 요약 노트"로 노출한다.
- 사람은 예외(`ESCALATED`)에서만 개입한다. 운영 초기에는 발행 직전 승인 토글을 켠다.

## 2. 범위

### 포함

- 도메인 모델, 상태 기계, 오케스트레이션 규칙, 평가 엔진, 가드레일
- 에이전트 입출력 JSON 계약(프롬프트 본문은 포함하지 않는다. 계약만 고정한다)
- FastAPI 서비스 구조(패키지, 계층 책임, 내부 API, CLI, 비동기 모델)
- 영속화 형태(MongoDB 컬렉션)
- 발행 페이로드: 마크다운 → Tiptap 변환표, Post BE `CreatePostDto` 필드 매핑

### 제외

- 각 LLM 벤더 SDK 호출 세부(클라이언트 계층은 인터페이스만 정의)
- Post BE HTTP 호출 세부(`Publisher` 인터페이스와 실패 분류만 정의)
- 프롬프트 문구 자체(별도 파일로 버전 관리, 이 문서는 입출력 계약만 다룬다)
- 관리자 UI

## 3. 용어

| 용어 | 뜻 |
|---|---|
| 라운드(`PublishingRound`) | 파이프라인 실행 단위. 글 3편을 품는다 |
| 슬롯(`AgentSlot`) | 라운드 안의 에이전트 자리. `A`, `B`, `C`. 모델 벤더와 분리된 식별자 |
| 페르소나(`PersonaProfile`) | 작성자로서의 성향과 리뷰어로서의 평가 렌즈 묶음 |
| 모델 바인딩(`ModelBinding`) | 슬롯에 실제 모델(벤더, 모델 ID, 파라미터)을 연결한 것 |
| 초안(`PostDraft`) | 글 한 편의 작업 단위. 버전과 리뷰를 품는 Aggregate Root |
| 버전(`DraftVersion`) | 초안의 특정 시점 본문. v1, v2, v3 |
| 리뷰(`PeerReview`) | 리뷰어 하나가 버전 하나에 낸 평가. `ReviewItem` 목록과 판정 |
| 지적 사항(`ReviewItem`) | 위치·심각도·내용·대안을 가진 불변 값 객체 |
| 해소 기록(`ItemResolution`) | 작성자가 지적 사항 하나에 내린 수용/기각 결정. 다음 버전에 속한다 |
| 전체 리뷰(`FULL`) | v1에 대해 두 리뷰어가 모두 수행하는 리뷰 |
| 재확인(`SPOT_CHECK`) | 직전 리뷰 완료 버전의 `open_blocking_items` 중 본인 지적이 남은 리뷰어만 수행하는 좁은 범위 리뷰 |
| 중재(`ARBITRATION`) | 작성자와 리뷰어가 CRITICAL 항목에서 교착했을 때 제3 에이전트가 내리는 판단 |
| 격리(`ESCALATED`) | 자동 수렴 실패. 사람의 판단을 기다리는 상태 |

## 4. 설계 원칙

1. **결정론적 제어, 확률적 생성.** 글과 리뷰는 LLM이 만들지만, 상태 전이·판정·종료 조건은 오케스트레이터가 규칙으로 결정한다. LLM의 `verdict`는 참고값이고 최종 판정은 `severity` 집계로 도출한다.
2. **슬롯과 모델의 분리.** 도메인은 `AgentSlot`(A/B/C)과 `PersonaProfile`만 안다. 어떤 벤더의 어떤 모델이 슬롯을 맡는지는 설정(`ModelBinding`)이다. 모델 교체·A/B 테스트가 도메인 수정 없이 가능해야 한다.
3. **렌즈는 모델이 아니라 (글, 리뷰어) 쌍에 배정한다.** 모든 글이 "논리/가독성", "팩트/구조", "비판/실무" 세 렌즈를 빠짐없이 받도록 매트릭스를 짠다.
4. **글 단위 독립 파이프라인.** 배리어는 주제 확정 단계에만 둔다. 이후 글 3편은 서로를 기다리지 않는다. 한 편의 격리가 나머지 발행을 막지 않는다.
5. **모든 LLM 호출은 기록된다.** 시도마다 `AgentCall` 영수증을 남겨 보낸 메시지, 출력, 토큰, 지연을 추적한다. 그 사용량 합계가 글 예산 상한의 입력이다.
6. **LLM 앞에 결정론적 게이트.** 구조 검증, 코드 블록 문법 검사, 길이, 스키마 검증, Tiptap 변환 가능 여부는 LLM 리뷰 전에 코드로 거른다.
7. **재시작 가능.** 상태는 전부 DB에 있다. 프로세스가 죽으면 마지막으로 저장된 상태부터 이어 가고, 진행 중이던 단계의 호출만 다시 한다.
8. **규모에 맞는 실행.** 워커 1개 안에서 글마다 코루틴 하나가 호출과 반영을 함께 한다. 작업 큐·분산 lease·다중 문서 트랜잭션을 두지 않는다(04 문서 1절, 07 문서 D-25).

## 5. 전체 흐름

```
[라운드 시작]
   │
   ▼
Phase 1  주제 제안 ──► 중복 판별·배정 ──► 3개 주제 TOPIC_LOCKED      ◄── 유일한 배리어
   │
   ├────────────────────┬────────────────────┐
   ▼                    ▼                    ▼
Post A (슬롯 A)      Post B (슬롯 B)      Post C (슬롯 C)        ◄── 이후는 글마다 독립
   │
Phase 2  초안 v1 작성 ──► VALIDATING(결정론적 게이트)
   │
Phase 3  FULL 리뷰 ×2 (나머지 두 슬롯, 블라인드)
   │
Phase 4  평가 엔진
   ├─ CRITICAL·MAJOR 0건 ───────────────────────────────► READY_TO_PUBLISH
   └─ 그 외 ──► REVISING: 작성자가 v(n+1) + ItemResolution 작성 ──► VALIDATING
                    │
Phase 5             ▼
            SPOT_CHECK (open_blocking_items 에 본인 항목이 남은 리뷰어만)
              ├─ 해소 ─────────────────────────────────► READY_TO_PUBLISH
              ├─ 미해소 & 작성자 기각 CRITICAL 존재 ──► ARBITRATION(제3 슬롯) ──► 판정에 따라 분기
              ├─ 미해소 & iteration < MAX ─────────────► REVISING (cause=REVIEW, iteration +1)
              └─ 미해소 & iteration = MAX ─────────────► ESCALATED
                                                           ├─ (사람: 그대로 발행) ──► READY_TO_PUBLISH
                                                           ├─ (사람: 폐기) ────────► REJECTED
                                                           └─ (사람: 지시문 재수정) ► DRAFTING(HUMAN) ► VALIDATING ► READY_TO_PUBLISH
   │
   ▼
READY_TO_PUBLISH ──(승인 토글 off 또는 사람 승인)──► PUBLISHED (+ 피어 리뷰 요약 노트)
```

`iteration` 은 0에서 시작한다. 리뷰 반영으로 수정을 시작할 때만 1 증가한다(03 문서). 게이트 재시도와 사람의 재수정 허가는 세지 않는다.

호출 횟수는 상한으로 쓰지 않는다. 재시도와 게이트 재작성을 빼면 글 1편의 최솟값은 4(주제 1, 초안 1, FULL 리뷰 2)이고, 리뷰 반영 수정은 최대 2회다. 중재는 교착 항목마다 1회라 항목 수만큼 늘어난다. 글이 멈추는 상한은 반복 횟수, 게이트 재시도, 호출 재시도, 글 토큰 예산이다.
